# Changelog

All notable changes to schist are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **Concept aliases now resolve on the read paths (#489), and `add_concept_alias` validates what it stores (#481/#490/#495).** Previously the tool wrote `concept_aliases` rows that no read path ever consulted. Now: `list_concepts` returns `aliasOf` (this slug is a duplicate of that canonical) and `aliases` (duplicates pointing at this canonical); `get_context`'s hot concepts flag duplicates with `aliasOf`; `get_note` on a concept note reports `alias_of`/`aliases`; and the CLI `context` command prints `(alias of X)` on annotated hot concepts (MCP/CLI parity). All annotations degrade gracefully on pre-alias-era indexes lacking the table. Write-side, the tool now rejects self-aliases post-normalization (`Machine Learning` → `machine-learning` counts as self, #490/#495), returns `NOT_FOUND` naming the missing slug instead of a bare FK failure (#481), and maintains a flat depth-1 alias forest so a single hop fully resolves: aliasing *to* a duplicate is rejected with the root suggested, re-aliasing a duplicate repoints it (`replaced_canonical` in the response) rather than accumulating a second canonical, demoting a canonical repoints its existing duplicates (`repointed`), and reversing an alias flips direction without leaving a chain. Ingest additionally sweeps self-referential rows written by older servers, next to its existing orphan prune.

### Security
- **Hub identities can now be pinned to SSH keys instead of trusted from client-sent env (#502).** Previously the pre-receive hook believed whatever `SCHIST_IDENTITY` the spoke shipped over `SendEnv`, so any spoke could push as any participant (including a `write: ["*"]` one) — the entire vault.yaml write ACL was advisory against a misbehaving spoke. New pieces: (1) `schist-shell`, a forced-command SSH wrapper that derives `SCHIST_IDENTITY` from the authorized key (overwriting any client assertion), marks the push pinned via `SCHIST_IDENTITY_PINNED=1`, and confines the key to `git-receive-pack`/`git-upload-pack` on the pinned repository through `git shell` (repo confinement baked in by `key add`, opt out with `--any-repo`; `git-upload-archive` deliberately excluded; `LD_*`/`DYLD_*`/`BASH_ENV` scrubbed before exec); (2) `schist hub key add|list|remove`, which manage `restrict,command="schist-shell <participant> <repo>"` entries in the hub user's `authorized_keys` (flock-serialized atomic 0600 writes, re-pin-by-blob on rotation collapses duplicate blob lines, participant validated against hub vault.yaml), plus `schist hub security require-pinned-identity on|off` to flip the toggle via the same git-plumbing path as other hub ACL mutations; (3) a `security.require_pinned_identity` vault.yaml toggle — when true, pre-receive rejects SSH pushes lacking the pinned marker (local pushes on the hub host stay exempt: filesystem access is admin authority, matching `schist hub`'s trust model); (4) `schist doctor --hub-path` checks: FAIL on un-pinned authorized_keys entries while enforcement is off (WARN once it's on — enforcement already rejects their pushes and un-pinned shell keys are the normal shape of admin login keys), WARN on unkeyed participants / stale pins / enforcement off, plus an `AcceptEnv` scan (effective config via `sshd -T` when runnable, file scan otherwise) warning on `SCHIST_*`, `*`, `PATH`, `LD_*`/`DYLD_*`, `PYTHON*`, `BASH_ENV`, and `GIT_*`-except-`GIT_PROTOCOL` forwarding. `doctor` gained `--authorized-keys` for non-default key file locations and hints when the hub repo belongs to a different user than the scanned key file. The `security:` block is parsed fail-closed by the CLI (unknown keys / non-bool values are validation errors) and deliberately ignored by the MCP server's lenient `loadVaultAcl` (hub-only, like `rate_limits` — no parser skew). Enforcement is opt-in; existing deployments are unaffected until the toggle is set.

### Removed
- **BREAKING:** Retired the `domain` concept. Closes #146. Dropped from every layer: vault.yaml top-level `domains:` field; note frontmatter `domain:`; SQLite `docs.domain` column and standalone `domains` table; `cli/schist/seed-domains.sql`; CLI `schist assign-domain` subcommand; MCP `list_domains` and `assign_domain` tools; `Domain` and `ListDomainsResponse` TypeScript interfaces. Field was 1.5% adopted (6/384 vault notes) with no registry in vault.yaml; never queried in any read path. Tags + concepts cover the same need. Migration: callers of removed tools/commands receive `unknown tool`/`unrecognized subcommand`; existing `domain:` keys in note frontmatter are now ignored by ingest (no rewrite needed); the SQLite `docs.domain` column is dropped on the first post-upgrade ingest since `docs` is DROP+CREATE'd every commit; the `domains` table is dropped likewise. **Deployment ordering matters:** rebuild `mcp-server/dist/` (`cd mcp-server && npm run build`) and restart Claude Code / Claude Desktop *alongside* `uv tool install --reinstall <path-to-cli>`. If the new `schist-ingest` runs (e.g. on a post-commit hook fire) while the OLD MCP server `dist/` is still loaded, the OLD server's `ensureSchemaCurrent` will see `domain` missing, attempt a rebuild that doesn't restore it, and throw a misleading `Schema drift persists after schist-ingest rebuild ... The installed schist-ingest is likely older than this MCP server` error — the actual fix is to rebuild MCP, not reinstall `schist-ingest`. `schist doctor` now flags this skew up front via the `MCP schema alignment` check.

### Added
- `schist doctor` gained an `MCP schema alignment` check that compares the configured MCP server dist's `REQUIRED_DOCS_COLUMNS` against the canonical `docs` columns from `schema.sql`. Warns when the MCP dist expects columns the current schema no longer defines (the OLD-MCP / NEW-ingest skew described above), pointing the user at the actual fix (rebuild MCP dist) rather than the misleading runtime error from `ensureSchemaCurrent`. Skips silently when no MCP entry is configured or when the dist predates the drift-detection feature (#145).
- `schist doctor` gained a `Skill tool references` check (#165) that cross-references every `mcp__schist__<tool>` reference under `<vault>/shared/skills/` against the live tool set parsed from the installed MCP server's `tool-registry.js`. Warns when a skill calls a tool the server no longer exposes, distinguishing known-removed tools (present in the `REMOVED_TOOLS` tombstone map, reported with replacement guidance) from unknown names (likely typos or a missed rename). Catches the failure mode where a removed MCP tool leaves dangling call sites in shared skills — e.g. the `request_capabilities` removal (#72) that lingered in `/learn`, `/handoff`, `/improve-skill`, and `/audit-skills`. Follows symlinks so symlinked-into-vault skills are scanned; skips silently when no MCP entry is configured or no `shared/skills/` directory exists.
- `schist doctor` gained a `Spoke identity` fail-fast check (#164): spoke vaults now FAIL when neither `SCHIST_IDENTITY` nor `GL_USER` is set, because the hub pre-receive hook will reject background pushes even if MCP's local ACL UX check can fall back to the agent owner. A shared `identity-resolution.cases.json` fixture now pins the hub (`resolve_identity`) and MCP (`resolveAclIdentity`) precedence chain across Python and TypeScript, including the intentional MCP-only owner fallback.
- MCP gained `sync_status` and `sync_retry` tools (#135). `sync_status` is read-only and reports spoke/hub heads, ahead/behind counts, working-tree cleanliness, and the last background sync sentinel with bounded git calls. `sync_retry` is identity-gated, supports explicit `push-only` and `pull-rebase-push` modes, awaits any in-flight background push, never force-pushes, aborts conflicted rebases, treats ACL/pre-receive rejection as non-retriable, and clears `.schist/last-sync-error` only after a successful push when the sentinel has not changed.

### Added
- **Background spoke pushes now classify their failures, and a diverged spoke recovers itself (#501, #500).** `triggerSpokePush` ran the push with `capture: false`, so every failure collapsed into the sentinel as `push exited with code 1` — a diverged spoke (fixable in seconds), an out-of-scope write (never fixable by retry) and an unreachable hub were indistinguishable, and diagnosing one meant a manual `git push --dry-run`. The push now captures output and records `push failed [<class>]: <tail of git's own output>`, where class is one of `non-fast-forward`, `acl-rejected`, `rate-limited`, `transport`, `stale-git-state`, `timeout`, `spawn-failed`, `other`. Classification order is load-bearing and pinned by tests against real CLI transcripts: rate limiting is decided before ACL (both arrive wrapped in git's generic `pre-receive hook declined` line, and calling a rate-limited push an ACL violation marks a retriable failure permanent), and a stale ref is decided before both. `isAclRejection` also stopped keying on two strings that never meant ACL: `push rejected by hub`, which the CLI prints for *any* push output containing "rejected" — including git's `! [rejected]` on every non-fast-forward — and a bare `acl` substring, which matches any host or path containing those letters (oracle, tentacle) while git echoes the remote URL on nearly every failure. Both defects also made `sync_retry` answer `retriable: false, reason: "ACL violation"` for a spoke that had merely fallen behind. Note a push killed by the 30s MCP budget is classified `timeout`, not `transport`: ssh's own connect timeout is longer, so an unreachable hub usually exhausts the budget before printing a transport error. `sync_status` exposes the parsed class as `last_sync_error.failure_class` (null for pre-#501 sentinels, which carry no marker). Building on that, a push rejected as `non-fast-forward` now triggers exactly one bounded `sync pull` (rebase) + `sync push` — never a force-push, only from a clean working tree with no git operation already in progress, and aborting the rebase on conflict so the tree is left as it was found. A dirty tree or an in-progress operation records the classified reason plus the command to run instead. Scope worth knowing: recovery fires when divergence is first detected, which is before any sentinel exists — once one does exist, the #75 write gate blocks the MCP writes that would trigger another push, so recovery does not retry itself and `sync_retry` remains the way out. Previously the only self-healing case was stale git state; a spoke that had merely fallen behind failed identically forever until a human ran `sync_retry mode=pull-rebase-push`.

### Fixed
- **A remote host whose name contains the word `acl` no longer turns every transport failure into a permanent ACL violation (#535), and `sync_retry` now returns the failure class it already knew (#534).** #501 narrowed `isAclRejection`'s bare `acl` substring to a word-bounded `\bacl\b`, which fixed the hostnames it was tested against (`oracle.example.com`) and left the ones it wasn't: a remote at `acl.internal` or `acl.company.com` has non-word characters on both sides, so a plain `Connection refused` against such a host matched, classified as `acl-rejected`, and came back `retriable: false` — #500's recovery never fired and the operator was pointed at the vault ACL while the real fix was to wait for the network. The word is gone from the matcher entirely, because no rejection path emits it: `pre_receive.py` says `out-of-scope writes`, `cannot determine push identity`, `unknown identity`, or the pinning message, and git wraps *every* pre-receive refusal in `(pre-receive hook declined)` — which catches all of them, including `failed to load vault.yaml`, whose own text carries no hub-specific phrase at all. The existing regression test could not have caught this: `oracle` has a word character before `acl`, so it passed with or without the word boundary. Separately, `syncFailureResponse` called `isAclRejection` directly instead of going through `classifyPushFailure`, bypassing the ordering that exists precisely because a rate-limit refusal arrives wrapped in the same `pre-receive hook declined` line — so a rate-limited retry was reported `retriable: false, reason: "ACL violation"`, the mis-attribution #501 fixed on the classification path reached again through the response path. Both now derive from one classifier, and `SyncRetryResponse` carries `failure_class` inline so an agent can pick its next retry mode without a second `sync_status` round-trip or parsing `message`. Routing `retriable` through the class exposed a second distinction the old code got right by accident: the hub enforces *two* rate limits with opposite recoverability. `git_syncs_per_hour` is a sliding window and prints `Retry after: N seconds`; `notes_per_sync` is stateless with `retry_after=0` and prints no such line, so the identical push is rejected identically forever and the fix is to split it, not to wait. Both classify as `rate-limited`, so `retriable` now requires the positive evidence of a retry window rather than the limit's name — an unrecognized future stateless limit reads non-retriable, stopping an agent instead of looping it — and the no-window case reports `reason: "Rate limit (no retry window)"`. Documented under Troubleshooting in `docs/hub-spoke-setup.md`, including that splitting into more commits does not clear `notes_per_sync` — the hook counts `oldrev..newrev` and dedupes, so the cap is per push RANGE and the remedy is a per-ref push or a raised limit. Reviewing the above turned up three more places the same "classify on hub-owned tokens, not on words that can appear anywhere" rule was not being followed, all of which `retriable` now depends on. (1) The `rate limit` test was a bare substring over combined stdout+stderr, and two purely LOCAL failures echo vault paths into it verbatim — the ignore guard's blocking list and the pre-commit secret scanner's matches — so a note named `rate limit notes.md` classified as rate-limited, and anyone with vault write could steer both the class and the retriability of an unrelated failure; it also swallowed the hub's own fail-OPEN warning (`RATE_LIMIT_BYPASSED — rate limit DB unavailable`), which *allows* the push. Now anchored on `REJECTED: rate limit exceeded (<limit>:` with the limit named. (2) `schist-shell`, #511's forced command, refuses BEFORE receive-pack starts — wrong repo, wrong verb, interactive shell — so there is no hook and no `pre-receive hook declined` wrapper, and the spoke sees only the message plus git's `Could not read from remote repository.`, which matches no transport pattern either. The clearest possible refusal fell through to `other`/retriable, so an agent whose key is confined to another repository would retry forever; the `schist-shell:` prefix is now an ACL signal. (3) `pre_receive.py` distinguishes `REJECTED:` (your push) from `ERROR:` (the hub) on purpose, and its diff-timeout path says "the hub may be under load; please retry the push" — but both return 1, so git wraps both in the declined line and keying on the wrapper answered "ACL violation, non-retriable" to a hub explicitly asking for a retry: the #535 mistake from the opposite direction. Hub-transient markers are now tested before the ACL matcher, anchored on that `ERROR:` prefix rather than the bare phrases — a second review pass caught that the unanchored form had reintroduced the very bug it was added alongside, and in the worse direction: `failed to diff` is two common words, the hub-transient test is the FIRST text test, and `transport` is the class #531's gate treats as self-clearing, so a note named `failed to diff.md` echoed by the ignore guard could have turned any push failure into an OPEN write gate. A steerable substring that opens a gate is worse than one that closes it. Finally, `failure_class` is populated on the **push phase only**: `syncFailureResponse` is shared with the pull-rebase path, and running a pull outcome through a push classifier can hand an agent a class that means something else entirely — `sync pull`'s conflict guidance prints `--identity <name>` and rebase echoes commit subjects, which embed note titles verbatim, so a note titled with "rejected" satisfies the identity+rejected clause and a pull comes back `acl-rejected`. The `sync_retry` ACL test's stub was emitting `Push rejected by hub: ACL violation` — this module's own `reason` string fed back as though git had printed it — and passed only because the matcher still keyed on the invented word; it now emits real `pre_receive.py` + git output.
- **`schist sync push` no longer reports success when git fails (#467).** Two call sites read a non-zero git exit as "nothing to do": `git_ops.has_uncommitted_changes` returned `bool(stdout.strip())` without checking `returncode`, and `sync_push`'s `git diff --cached --name-only` built its staged-file list from an empty stdout. A corrupt `.git`, a held index lock, a missing git binary, or a permissions problem therefore produced `Nothing to push` and exit 0 while the vault silently diverged. Both now behave like `has_unpushed_commits`, which had it right: the former answers conservatively (claim there IS work, so the real failure surfaces from the stage/commit path with git's own message), the latter fails loudly with git's stderr and leaves the files staged for the next attempt.
- **`schist doctor` no longer reports PASS for a post-commit hook git will never run (#460).** The check tested only that the file existed. Git silently skips a hook that isn't executable, so a `chmod -x`, a restrictive umask, or a copy that dropped the mode bit disabled auto-ingest while doctor stayed green and the SQLite index drifted from the notes on disk. Non-executable now FAILs with the `chmod +x` fix. (`schist init` installs hooks `0o755`, so this only reports genuinely broken installs.)
- `schist doctor --hub-path` no longer reports wildcard writers as lacking every directory (#512). The ACL-drift check's cross-participant signal built its holders map from concrete scope strings only, so an admin identity with `write: ['*']` was never counted as a holder and was listed as "lacking" every dir any other participant held — a guaranteed false positive (nine lines on the production hub) for any hub with an admin identity. Both sides of the sentence now reflect effective coverage via `_scope_matches` (as the first signal already did): a participant is only "lacking" a scope when no grant of theirs covers it — which also stops a parent grant (`research`) from being reported as lacking a child (`research/mario`) — and the "held by" list now names wildcard and parent-grant holders too, instead of only those who spell the dir out literally.
- Removed the `rate-limits.sqlite` database accidentally committed to the repo root in #524, and fixed the test leak that created it (#525). `check_rate_limit` defaults its DB to `$GIT_DIR/rate-limits.sqlite` and falls back to the working directory, so `TestMainPinning`'s allow-path tests — which reach the rate-limit check without a `db_path`, unlike `TestMain` — wrote into whatever directory pytest ran from. Those tests now pin `GIT_DIR` to `tmp_path`, `.gitignore` covers the filename at any depth rather than just `cli/`, and a new autouse fixture in `cli/tests/conftest.py` fails any test that creates or writes a GIT_DIR-derived runtime artifact — the rate-limit DB or the pre-receive audit log, whose default path has the same CWD fallback — in the working directory or the repo's `cli/` and `hooks/` dirs, so the next instance is caught in CI rather than in a commit. `.gitignore`'s two directory-anchored `rejected-pushes.log` entries were collapsed into one depth-agnostic entry for the same reason.
- Pending spoke sync failures now block subsequent MCP vault writes until sync recovery succeeds (#75). `create_note` and `add_connection` return `SYNC_DIRTY` when `.schist/last-sync-error` exists, preventing agents from compounding spoke/hub divergence; `get_context` now surfaces the warning without clearing it, and `sync_retry` or a successful background push remains the recovery path.
- `schist sync` gained stale git-operation recovery for spoke pushes (#143). `sync pull` still self-heals leftover rebase state, and `sync push --force` / `sync --force` now clears stale rebase, merge, and `.git/index.lock` state before retrying. MCP background `triggerSpokePush` detects stale git state after a failed push, retries once with `sync push --force`, clears an unchanged `last-sync-error` sentinel after successful pushes, and write-tool `syncWarning` messages now include the sentinel age.
- `schist sync push` now stages existing canonical content directories for logical `scope: global` instead of trying `git add global/`, and now fails explicitly if staging the configured scope fails. Fixes the misleading "Nothing to push" path when global-scope spokes had dirty tracked files under directories like `concepts/` (#79).

### Added
- `confidence` field on docs schema and `create_note` MCP tool. Optional enum (`low | medium | high`); omitted from frontmatter when not declared. Ingestion populates `docs.confidence` (NULL when undeclared — deliberately distinct from "agent said medium"). `search_notes` accepts an optional `confidence` filter that selects matching docs and excludes NULL-confidence rows. `get_note` returns the field when set, omits it when NULL. Closes #69.

### Changed
- **Removed MCP tools now return a `TOOL_REMOVED` error with replacement guidance instead of a bare `Unknown tool` (#165).** The server keeps a `REMOVED_TOOLS` tombstone map (`tool-registry.ts`); the `index.ts` router looks up unknown tool names against it via `Object.hasOwn` (not `in`, which would match prototype members like `constructor`/`toString` for client-controlled names). Stale callers — skills, clients that cached an old tool list, pasted snippets — get a self-correcting message rather than an unactionable error. First entry: `request_capabilities` (removed in #72), explaining that write tools are now callable directly. `TOOL_REMOVED` added to the `ToolError` code list in `types.ts`.
- **Flat `scope_convention` is now the default for new vaults.** `schist init --hub` and `schist init` (standalone) seed `scope_convention: flat` with per-participant `default_scope: global` (previously `subdirectory` with per-spoke `default_scope: research/<spoke>`). Authorship is recorded in the auto-filled `source_agent` frontmatter, not via directory placement. Hub seeds now grant each participant write on the content-axis dirs `[research, concepts, decisions, notes, ops, papers]`. `scope_convention: subdirectory` and `multi-vault` remain fully supported for existing deployments (no deprecation); existing `vault.yaml` / `.schist/spoke.yaml` files are not touched. v0 vaults (no `vault_version`) still default to `subdirectory`.
- **Single source of truth for content-axis directories.** The canonical directory list moved to `cli/schist/default.yaml` (shipped in-package; the old `schema/default.yaml` is removed) and expanded to all eight content-axis dirs (`notes, papers, concepts, research, decisions, ops, projects, logs`). Both the Python rate limiter (`rate_limit.py`, fail-closed) and the MCP server (`tools.ts` `loadVaultConfig`, fail-open with a drift-tested baked-in mirror) now derive their directory list from it instead of each carrying a separate hardcoded copy.
- **`notes_per_sync` rate-limit counting change for `subdirectory` hubs.** Under `scope_convention: subdirectory`, the pre-receive hook now counts files under all content-axis dirs (adds `research/`, `decisions/`, `ops/`, `projects/`, `logs/`) toward `notes_per_sync`; previously only `notes/`, `papers/`, `concepts/` were counted (a silent under-count). Operators running active subdirectory hubs with tight `notes_per_sync` limits may need to raise the limit in `vault.yaml`. `flat` / `multi-vault` conventions are unaffected (they count by `.md` suffix).
- **`schist init --scope-prefix` is deprecated and ignored.** Flat-convention hubs do not use a per-participant scope prefix. The flag is retained for backward-compat (passing it no longer errors); `init --hub` warns on stderr when a non-default value is supplied.
- **BREAKING:** Vault-write MCP tools (`create_note`, `add_connection`, `assign_domain`) now require an `owner` argument and validate it via `validateOwner` against `SCHIST_AGENT_ID` / `SCHIST_ALLOWED_AGENTS`, mirroring the memory-write policy from #61. The validated owner is stamped on `source_agent` frontmatter (replacing the hardcoded `"mcp"`) and the git commit message (`— by {owner}` instead of `— via MCP`). Closes #63. Callers must now pass `owner` on every vault write or receive `CONFIG_ERROR` / `VALIDATION_ERROR`; deployments must set `SCHIST_AGENT_ID` or `SCHIST_ALLOWED_AGENTS` in the MCP server's environment.
- **Bug fix:** `validateOwner` now canonicalizes the incoming owner by trimming whitespace before comparing against `SCHIST_ALLOWED_AGENTS` (which is itself trimmed at parse time). Pre-fix the trim was asymmetric — a caller sending `owner="atwood "` was rejected even when `"atwood"` was in the allowlist. The function now returns the canonical (trimmed) owner string; vault-write and memory-write tools assign it back so `source_agent` frontmatter, git commit subjects, and `agent_memory.owner` rows all store the canonical form (no silent key-splitting from trailing whitespace). Surfaced by adversarial review of #131.

### Added
- Startup warning when neither `SCHIST_AGENT_ID` nor `SCHIST_ALLOWED_AGENTS` is set — every write tool will return `CONFIG_ERROR` until one is configured. Replaces silent first-write failure with a loud signal at MCP server startup.

## [0.2.0] - 2026-05-23

### Added
- `schist doctor` command — one-command health check for schist setup (Python, Node, Git, vault, SQLite, hooks, MCP config)
- `schist init --print-mcp-config` — generates ready-to-paste MCP server config for Claude Code and Cursor
- `docs/getting-started.md` — linear onboarding guide with platform-specific instructions (Linux, macOS, HPC)
- `docs/hub-spoke-pi-orcd-dragonfly.md` — opinionated topology guide for Pi hub + orcd (HPC) + dragonfly (Mac) spoke setup
- `schist doctor` reports `uv` availability (WARN if missing — pip still works as a fallback). Note: hosts without `uv` will now show one new `[WARN] uv: not found` line in the default check output; downstream scripts that scrape doctor output to assert "no warnings" may need adjustment.
- `cli/uv.lock` — checked in for reproducible source installs across Mac / Pi / HPC. CI enforces freshness via `uv lock --check` to catch pyproject.toml edits that forget to regenerate the lock.

### Changed
- **Docs:** `docs/mcp-setup.md` adds a comprehensive **Cursor pagination protocol** section covering all cursor adopters, the worked example for cursor consumption, identical-query refusal semantics, the full cursor error-code table, the `query_graph` server-pagination behavior, and reason-string verbose for `search_memory` + `get_context`. This completes #50 PR 8 — the migration documentation for the 7-tool cursor protocol rollout. Tool registry descriptions are already self-documenting (each cursor adopter advertises pagination + 300s refusal in its description string from PRs 3–7).
- **BEHAVIOR CHANGE:** `get_context` MCP tool — `depth: "full"` now requires `verbose: "<reason ≥12 chars>"` to actually compute the `tagCloud` field. Without a valid reason, the server silently downgrades to `depth: "standard"` and the response carries a `verboseNote` hint indicating the upgrade path. No error is raised on missing/whitespace-only verbose — agents that lazily ask for "full" still get a usable standard response. Type misuse (`verbose: true`) and length misuse (string <12 code points) are rejected as `INVALID_ARG`. The `verbose` field is validated for type on all depths, but its semantic effect (gating tagCloud) only applies on `depth: "full"`. Refs #50 (PR 7 of the context-efficiency rollout).
- **BREAKING:** `list_concepts` MCP tool now returns `{ concepts: Concept[], cursor?: string }` instead of a bare `Concept[]` array, and accepts new `cursor` and `limit` inputs. Pagination is cursor-based with a stable `ORDER BY slug ASC` tiebreaker. Default `limit` is 50; hard cap is 200. Callers that previously iterated `response` as an array must now destructure: `const { concepts } = response`. Refs #50 (PR 6 of the context-efficiency rollout).
- **BREAKING:** `list_domains` MCP tool now returns `{ domains: Domain[], cursor?: string }` instead of a bare `Domain[]` array, and accepts new `cursor` and `limit` inputs. Pagination is cursor-based. Default `limit` is 100; hard cap is 500. Callers that previously iterated `response` as an array must now destructure: `const { domains } = response`. Refs #50 (PR 6 of the context-efficiency rollout).
- `list_domains` now applies a default `limit: 100` (cap 500). Previously unbounded — a footgun on vaults with hundreds of domains. Refs #50.
- **BREAKING:** `query_graph` MCP tool is now server-paginated. The server wraps every caller query as `SELECT * FROM (<caller_sql>) AS user_query LIMIT N OFFSET M` where N defaults to 100 and caps at 1000. A caller running `SELECT * FROM docs` on a 1000-doc vault used to get all 1000 rows; it now gets 100 rows + a `cursor` token. The caller's own `LIMIT` / `ORDER BY` / `OFFSET` inside the SQL are respected verbatim — a caller passing `SELECT * FROM docs LIMIT 5` still gets exactly 5 rows (no cursor, since 5 < 100). Pass the cursor on the next call to advance, or pass a `limit` arg (up to 1000) for one-shot larger results. Response shape gains an optional `cursor` field; `columns` / `rows` / `rowCount` unchanged. Identical queries within 300s without a cursor are refused with `CURSOR_REQUIRED`. Refs #50 (PR 5 of the context-efficiency rollout). Concurrent-ingest caveat: see the spec's "Concurrent-ingest limitation" subsection — long pagination across ingest commits can skip or duplicate rows; bounded by the 300s cursor TTL. Keyset-cursor migration tracked in #90.
- `search_notes` MCP tool now returns `{ results: SearchResult[], cursor?: string }` instead of a bare `SearchResult[]` array, and accepts a new `cursor` input. Pagination is cursor-based and deterministic (bm25 + id-ASC tiebreaker). Identical queries within 300s without a cursor are refused with `CURSOR_REQUIRED`. Default `limit` is unchanged (20); the hard cap is 100. Per spec, `search_notes` has no `verbose` mode — call `get_note` for full bodies. Refs #50 (PR 4 of the context-efficiency rollout).
- Node.js minimum version relaxed from >=22 to >=20 (no Node 22-specific features used)
- MCP server no longer requires `request_capabilities` before write tools — the gate provided no real access control and added friction in shared-MCP deployments (PR #76, closes #72, #73). Memory-write authorization continues to be enforced at the data layer by `validateOwner` against `SCHIST_AGENT_ID` / `SCHIST_ALLOWED_AGENTS`. Vault-write identity enforcement is tracked in #63.
- Recommended Python package manager for source installs is now [uv](https://docs.astral.sh/uv/) — faster installs, lockfile-aware. The published `pip install schist` end-user path is unchanged; dev installs should prefer `uv pip install --system -e ./cli`. Docs, CI, and error messages updated accordingly. pip remains a supported fallback.

### Removed
- `request_capabilities` MCP meta-tool. Calling it now returns `VALIDATION_ERROR: Unknown tool: request_capabilities` (PR #76).

### Fixed
- **Spoke-sync hardening (#122–#124).** Three follow-ups to the #120 fix:
  - **#122 concurrency cap:** `triggerSpokePush` now coalesces concurrent calls for the same vault via an in-flight `Set<vaultRoot>`. Pre-fix, a write-heavy session (e.g. distillation runs producing 20+ rapid `create_note` calls) spawned 20 detached `schist sync push` children — first grabbed `.git/index.lock`, rest failed with lock contention, each wrote a sentinel, agent saw an oscillating warning loop. The first push naturally batches subsequent commits via git push's current-HEAD semantics, so coalescing here loses no data; after the in-flight push exits, the next write spawns a fresh push for whatever's still ahead of the hub.
  - **#123 SCHIST_INGEST_BIN env var:** `schistCliBin()` is now parameterized — `schistCliBin("schist")` (honors `SCHIST_BIN`) and `schistCliBin("schist-ingest")` (honors new `SCHIST_INGEST_BIN`). Operators with multiple installs (e.g. `uv tool install` of two schist versions for testing) can now pin both binaries independently. Empty-string env values fall through to PATH defaults (`?.trim() || binName`). **Version-coherence note:** if an operator pins one binary but not the other, sync and ingest may run different schist versions — CHANGELOG documents the requirement but doesn't enforce it.
  - **#124 atomic sentinel write/clear:** `writeSyncError` now writes to `last-sync-error.tmp-<pid>-<ts>` then `fs.rename`s over the canonical path (POSIX-atomic on same filesystem) — concurrent readers can no longer observe a zero-byte truncate-in-progress state. `get_context`'s clear path now renames the sentinel to `last-sync-error.consumed-<pid>-<ts>` BEFORE reading and unlinking it — concurrent `readSyncWarning` calls from write tools either see the sentinel and surface the warning (before rename) or see ENOENT and report healthy (after rename), never an intermediate state. Closes the TOCTOU window between PR #121's write-path syncWarning surfacing and `get_context`'s clear.
- **Cursor protocol hardening (#108–#115).** Eight defensive improvements to the read-side cursor adopters surfaced by adversarial review of the #50 rollout:
  - **#108 limit validation:** `Number.isFinite` + `Math.trunc` defense against non-numeric / fractional / out-of-range `limit` args reaching `Math.min` with implicit string concat. Tool-registry schemas tightened to `{ type: "integer", minimum: 1, maximum: <cap> }` so well-behaved clients are rejected at the JSON-schema boundary; handler-level `validateLimit` is defense-in-depth.
  - **#109 cursor length cap:** `decodeCursor` rejects cursors longer than `CURSOR_MAX_LENGTH` (4096 chars) before base64 decode. A 100 MB cursor argument no longer triggers unbounded server memory allocation.
  - **#110 startup warning:** `index.ts` emits a one-time WARN when neither `SCHIST_AGENT_NAME` nor `SCHIST_AGENT_ID` is set, so multi-tenant deployments (e.g. OpenClaw shared-MCP) notice when the anonymous-bucket refusal-LRU collapse would happen.
  - **#111 `listDomains` error swallowing:** narrowed the `catch {}` in `sqlite-reader.ts` to swallow only the original "vault not initialized" sentinels (`SQLITE_CANTOPEN`, "no such table"). Unexpected errors (corrupt DB, locked DB) now propagate so the handler's `normalizeError(e, "INGEST_ERROR")` actually fires instead of silently returning `[]`. Previously the handler's catch was unreachable.
  - **#112 distinct error codes:** introduced `CURSOR_QUERY_MISMATCH` for cursor-passed-to-different-query (binding fail), keeping `CURSOR_INVALID_SIGNATURE` for HMAC fail. Pre-fix both surfaced as `CURSOR_INVALID_SIGNATURE` with confusingly-mixed messages. HMAC-fail message now reads "the server's signing secret likely rotated" so operators debugging "all my cursors broke after deploy" can tell the cases apart.
  - **#113 vaultRoot in refusal LRU key:** the LRU is now keyed on `(tool, queryHash, owner, vaultRoot)`. Single-vault-per-process deployments see no change; multi-vault setups no longer suffer cross-vault refusal collision.
  - **#114 carve-out documented:** the spec at `docs/superpowers/specs/2026-05-04-mcp-context-efficiency.md` now explicitly carves out the "results fit within limit → no recordIssued → identical follow-up not refused" case. No behavior change; documentation fills the spec gap.
  - **#115 unified `activeOwner` resolution:** new `resolveActiveOwner()` helper in `agent-identity.ts` consolidates the three different env-var chains the 5 cursor handlers used independently. NAME → ID → "" everywhere; per-call `args.owner` still takes precedence on `search_notes`. **Minor behavior change** for deployments setting both `SCHIST_AGENT_NAME` and `SCHIST_AGENT_ID` to *different* values: `query_graph` and `search_memory` (previously ID-only) now use NAME-first like the vault-DB tools. Most deployments set just one env var and are unaffected.
- **`triggerSpokePush` / `maybeSpokePull` now spawn the `schist` console-script** instead of `python3 -m schist` (#120). The `python3 -m schist` form fails silently on hosts where schist is installed via `uv tool install` or `pipx` — both produce the `schist` binary on PATH but install into an isolated venv, so `python3` has no importable `schist` module. Pre-fix this manifested as silent `ModuleNotFoundError` exits during write-heavy sessions: the sentinel `.schist/last-sync-error` recorded each failure but agents never saw the divergence until session end. The console-script approach matches the existing `schist-ingest` pattern at `triggerIngestion`. New `SCHIST_BIN` env var lets operators pin a specific binary path if needed.
- **Write-tool responses now surface `syncWarning`** when `.schist/last-sync-error` is present (#120). `create_note`, `add_connection`, and `assign_domain` read the sentinel on each successful response and include the failure message — without clearing. `get_context` still owns clearing (its existing behavior). This means a write-heavy session that diverges from hub sees the warning on every write rather than discovering the divergence at session end. The warning text points at `get_context` as the acknowledge path.
